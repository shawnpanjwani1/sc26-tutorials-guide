The whole tutorial in 5 sentences

  1. LLMs are random. The same question can get different answers, so one run proves nothing.
  2. Run many samples and report a probability (pass@k, speedup@k), not your best example.
  3. Log every input and output so others can replay your results instead of re-generating them.
  4. Report everything: model + version, sampling settings, prompts, human steps, cost/tokens, limitations.
  5. Don't trust a single judge (an LLM or a human). Prefer objective, reproducible checks (tests, runtimes, multiple-choice).
Why it matters: in normal HPC research a compiler is deterministic. Put an LLM in that loop (e.g. "LLM optimizes the GPU kernel → run & profile → repeat") and part of your method is now stochastic. You must evaluate it like any other noisy experiment.
GPU kernel→LLM optimization (random!)→optimized kernel→run & profile→repeat

Section 1 · slides 6–15

How an LLM works (just enough)

Plain English

  • An LLM is a neural network (a transformer) that reads text and outputs probabilities for the next token.
    "I have a pet" → dog 0.4 · cat 0.3 · … · cow 0.01 · chair 0.00001
  • Tokens are integer IDs for pieces of text. They are not exactly words or characters.
  • Generation = pick a next token, add it, repeat until a stop token. Small early differences snowball into very different answers.
  • Sampling: always picking the top token gives dull, repetitive text, so models pick randomly:
    • Temperature: low = safe/predictable, high = creative/random.
    • Top-k: choose only among the k most likely tokens.
    • Top-p (nucleus): choose among the smallest set of tokens whose probabilities add up to p.
    • Greedy: always the top token (temperature ≈ 0).

Where randomness comes from

  1. Sampling: random choice of the next token.
  2. Prompt variance: "Find the square root of N" vs "What times itself equals N?" are the same problem, different prompts.
  3. Hidden sources: GPU parallelism and floating-point order, mixture-of-experts routing, and commercial models silently changing weights or system prompts.
Remember this: with fixed weights and input, the model's probabilities are essentially deterministic (apart from small floating-point and batching effects). Most of the randomness comes from how you sample and how you ask.

Section 2 · slides 16–25

"How to lie with LLM results": the 9 traps

The heart of the tutorial. Each row: the mistake, and what to do instead.
1
Ignoring randomness: reporting one output.
Generate many samples, and vary the prompt too. Report a probability (mean accuracy, pass@k).
2
Mixing formatting with skill: int(answer)==truth fails on "The answer is 42".
Parse answers generously, unless formatting is part of the task.
3
Cherry-picking the best example or the only setting that works.
Report all results and all sampling parameters.
4
Benchmark leakage: the test questions were in the training data, so you measure memory, not skill.
Use private questions, and check they're not near-copies of public ones.
5
Too-simple metrics: MPI code that sends to every rank in a loop "works".
Also judge quality: the right answer is MPI_Bcast. Measure performance and idiom, not just "runs".
6
LLM-as-judge: small prompt or judge changes swing scores (rubric drift), and judges reward style over correctness.
Use as a helper only, never as the sole scientific evaluation.
7
Human-as-judge: hidden criteria, inconsistent people.
Publish the criteria and raw scores. Follow social-science practice for labeling.
8
Hidden human help: cleaning data between steps, tweaking prompts, swapping models.
Document every human intervention.
9
No cost reported. Better but 10× pricier?
Report $ or GPU-hours and token counts (prices change, tokens don't).

Designing experiments with a random part

7 ways LLMs show up in research (know which one you're doing)

RoleWhat the LLM doesHPC example
AnnotationLabels artifactsTag job logs as "memory-bound / MPI issue / IO bottleneck"
JudgeScores against a rubric"Is this optimization plausible?"
SynthesisCombines evidence, makes dataSummarize profiler reports; make synthetic test kernels
GenerationWrites code/configsKernels, MPI/OpenMP/CUDA, job scripts, compiler flags
Tools / agentsEmbedded in a toolPorting, performance debugging, workflow automation
BenchmarkingIs the thing being testedMany attempts on standard HPC tasks
SubjectPlays a userSimulated scientist or operator in a workflow study

Four techniques

  1. Structured outputs: force JSON with fixed fields, and retry if invalid. Less randomness, easier parsing (fixes Lie 2).
  2. Test each component alone: log the inputs and outputs of each agent step, and turn them into a small benchmark for that step.
  3. Ablations: remove one piece and see if results change. Demo 3: is "self-repair" really better than just spending the same attempts on fresh programs?
  4. Sanity-check by eye, even when humans aren't part of the method. Example: what if the "explain the profile" LLM starts writing optimizations itself?

Section 4 · slides 38–54

Transparency & reproducibility

Key idea: replay, don't regenerate

Big open models and commercial APIs can't be made bit-reproducible. So the generated outputs themselves are part of your artifact. Another researcher should be able to replay your logged outputs and get your numbers.

How to log

  • APIs: wrap calls in a logger. Tens of lines: intercept HTTP, hash the request, save the response, and in replay mode return the saved one.
  • Agent frameworks have tracing: OpenAI Agents SDK (on by default), LangChain LANGSMITH_TRACING=true, LlamaIndex mlflow.llama_index.autolog(), AutoGen (Python logging).
  • Anonymous review: anonymous.4open.science hosts files with names masked.
  • Never save API keys in logs.

What to report (7 items)

DeclarationAll LLM use, where and why. Prominent if central.
Models/versionsModel, version, quantization, software versions, sampling settings (defaults change!)
DesignPrompts, workflow, data flow between components
TracesActual outputs, with samples in the paper
Benchmarks & metricsWhy chosen; number of repetitions and all configs
ReferenceA human or open-model baseline next to commercial results
LimitationsLLM-specific risks
Main paper = what's crucial to the method. Supplement/artifact = full prompts and traces. Checklist inspired by Baltes et al., "LLM Guidelines".

Section 5 · slides 55–59

Human validation: when and how

Problem: people are inconsistent (even with themselves over time), hard to reproduce, and easily swayed. Longer, more technical answers "feel" better even when wrong.

Try it: which answer is better? (slide 59)

"Can this loop be safely parallelized with OpenMP?" for(i=1;i<n;i++) a[i] = a[i-1] + b[i];

A: "Yes, each iteration writes a distinct a[i]… here's the #pragma omp parallel for version, faster for large n." Confident, has code.
B: "No, a[i] reads a[i-1] from the previous iteration: a loop-carried dependence. A naive parallel for can change the result."

B is correct. A looks more helpful but is wrong. That's exactly why "which looks better?" is a bad human metric.

Do it right

  • Use humans as a supplement to reproducible metrics, never alone.
  • Publish all human scores and raw data. They are part of the method.
  • Ask humans to do something measurable with the output, not to vote on it:
    ✗ "Rate this performance explanation: good / ok / bad"
    ✓ "Use this explanation to optimize the code", then measure the speedup. Or "answer these multiple-choice questions using the summary".

Section 6 · slides 60–68

Baselines and metrics

Baselines

Compare with models of similar cost, speed, quality and availability, and with the frontier (state of the art). "Best open model" is a valid result, but still show the frontier for context.

Probabilistic metrics: the formulas, simply

Generate N samples per prompt (N much larger than k), count c correct, then ask: if the model gets k tries, how likely is at least one to be correct?

pass@k = 1 − C(N−c, k) / C(N, k)      (C = "n choose k")

Same idea, other uses: race@k = chance at least one of k attempts has a race condition. speedup@k = expected best speedup over k attempts (sequential baseline time ÷ generated code time). reg@k = expected minimum register use over k attempts. From Nichols et al., "Can Large Language Models Write Parallel Code?"

Try it: pass@k calculator
N samples correct c k →
Example: 3 of 10 samples correct. pass@1 = 30%, but pass@3 ≈ 71%. That's why you must say which k you report.
Watch for the trap in the dot-product example: #pragma omp parallel for with sum += and no reduction(+:sum) is a data race, so it's wrong even though it compiles and often "works". Correctness checks must catch this.

One-page checklist (use it on your next LLM project)

  • ☐ Many samples per problem, not one
  • ☐ Vary the prompt wording too
  • ☐ Report pass@k / mean, and state k and N
  • ☐ All sampling settings reported
  • ☐ Parse answers generously / structured JSON
  • ☐ Test set not in training data
  • ☐ Metrics cover quality and performance, not just "runs"
  • ☐ No LLM-only or human-only judging
  • ☐ Every human intervention written down
  • ☐ Every request and response logged, replayable
  • ☐ Model, version, quantization, software versions
  • ☐ Prompts and workflow described
  • ☐ Cost, GPU-hours and tokens
  • ☐ Ablation for each claimed component
  • ☐ Open-model or human baseline next to frontier models
  • ☐ Limitations section
Apply it: pick one place your team uses an LLM today (code generation, summarizing logs, labeling, an agent). Which boxes above does it tick? The cheapest wins are usually: log every request/response, sample more than once, and add an "LLM-off" baseline.

Self-check quiz

Answer in your head, then click to reveal.
1. Why is reporting one LLM output misleading?Outputs are random (sampling and prompt wording). Report a probability over many samples.
2. Your script marks "The answer is 42" wrong because it expects "42". Which lie?Lie 2, mixing formatting with skill. Parse generously or use structured output.
3. 2 of 20 samples are correct. Estimate pass@1. Is pass@5 higher or lower?pass@1 = 10%. pass@5 is higher (≈ 45%), because more tries means more chances.
4. Why can't you just rerun a GPT experiment to reproduce it?Sampling randomness, non-deterministic GPU math, and the provider can change the model. Log outputs and replay them.
5. What is rubric drift?Small changes in the judge's prompt or model swing the scores. It's why LLM-as-a-judge can't be the only evaluation.
6. Why report token counts and not just dollars?Prices change over time; token counts stay comparable.
7. Name a better human evaluation than "rate this explanation good/ok/bad".Have the person use the explanation for a task (optimize the code, answer multiple-choice) and measure the result.
8. What does an ablation tell you in the self-repair demo?Whether the gain comes from "repair" itself or just from spending more attempts. Compare against fresh samples on the same budget.
9. What is wrong with #pragma omp parallel for + sum += x[i]*y[i]?A data race on sum. It needs reduction(+:sum). Compiling and "seeming to work" isn't correct.
10. Which 7 things go in an LLM reporting checklist?Declaration, models/versions, design, traces, benchmarks & metrics, reference (human/open-model), limitations.
